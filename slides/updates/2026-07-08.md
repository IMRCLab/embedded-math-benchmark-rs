# C vs Rust on robot MCUs

## Project update 8 July 2026

---

## Reminder: What we're trying to find out

- MCUs: RP2040 (Raspberry Pico 1), STM32 (Crazyflie)
- Rust gives us memory safety without giving up low-level control. Does that cost speed?
- For now we're just making sure the measurements are trustworthy

---

## How it works: One config file

- One JSON file lists the tasks, libraries, repetitions, and inputs
- A build-time macro turns it into code, so the chips never parse JSON
- Code is grouped by task and library, and only the computation is timed
- Adding a library is a small struct plus one line in the config
- We stop the compiler optimizing the work away and run many reps

---

## What it produces

- Runs on the host (nanoseconds) and the Pico (real clock cycles)
- STM32 compiles but isn't running on the board yet
- One CSV row per platform, library, task, and input
- Each row has the timing and the actual result

## The CI pipeline

For the MCUs it's hardware-in-the-loop.

- Build: compile the binaries
- Run: flash the chips over a probe and capture output. The host just runs normally.
- Collect: read the logs, pull out the tagged rows, write one CSV
- Check: fmt and clippy

---

## Where it actually is

- The full path works: input json runs on chip, creates one CSV
  - For Pico 1 and host native
- STM32 isn't on the board yet, and the Pico 2 hasn't been started in Code
- So far it's Rust libraries against each other, not Rust against C
